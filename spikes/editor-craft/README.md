# Спайк: зеркальная сборка редактора на Craft.js (STUDIO-008)

Одноразовый спайк к [ADR-0004](../../docs/adr/ADR-0004-editor-base.md). Собран
**после** того, как ADR выбрал Puck, — чтобы сравнить кандидатов **эмпирически**
(объём кода, эргономика, грабли), а не по оценке. Зеркалит
[`spikes/editor/`](../editor/) (Puck) тип-в-тип: те же реальные модули
(`intro/envelope`, `hero`, `closing`), тот же агностичный `renderDocument`, та же
гипотеза ADR-0002 — редактор **оборачивает** строковый render, а не заменяет его.

> Не продакшн-код. Живёт в `spikes/`, вне `src/`, исключён из прод-сборки
> (корневой `tsconfig` не включает `spikes`), линта (`eslint.config.js`
> игнорирует `spikes`) и тестового прогона (`vitest` берёт только `src/**`).

## Запуск

```bash
# интерактивный редактор в браузере
npm run spike:craft         # → http://localhost:5173 (Vite)

# headless-проверка адаптера (без браузера), печатает PASS/FAIL
npm run spike:craft:verify
```

## Эмпирическое сравнение Craft.js vs Puck (по факту сборки)

Оба спайка делают **ровно одно и то же** поверх одного ядра. Разница — в том,
сколько обвязки редактора пришлось написать руками.

### Объём кода (фактический `wc -l`)

| Часть                               |                                          Puck |                    Craft.js |          Δ |
| ----------------------------------- | --------------------------------------------: | --------------------------: | ---------: |
| Адаптер модель↔редактор             |                    `puck-adapter.tsx` **175** | `craft-adapter.tsx` **230** |        +55 |
| Панель свойств из схемы             | внутри адаптера (`fieldsFromSchema`, ~**22**) |  `SchemaFields.tsx` **109** |        +87 |
| Палитра / Toolbox                   |                            **0** (из коробки) |        `Toolbox.tsx` **47** |        +47 |
| Каркас + выделение + экспорт        |                             `App.tsx` **142** |           `App.tsx` **223** |        +81 |
| **Код редактора (без verify/main)** |                                      **≈317** |                    **≈609** |  **≈1.9×** |
| verify.mts (доказательство)         |                                           136 |                         148 |        +12 |
| **Итого**                           |                                       **469** |                     **773** | **≈1.65×** |

> На Craft.js вышло **примерно вдвое больше кода редактора**. Весь прирост —
> ровно те части, что Puck даёт батарейкой: палитра, декларативная панель полей,
> каркас с DnD и выделением.

### Что пришлось писать руками (и чего не было у Puck)

- **Палитра** (`Toolbox.tsx`, 47 строк). У Puck — часть `<Puck>`; здесь — сам
  компонент + `connectors.create` на каждый тип.
- **Панель свойств** (`SchemaFields.tsx`, 109 строк). У Puck `fieldsFromSchema`
  (~22 строки) отдаёт схему Puck, а всю разметку полей, лейблы, слайдеры и
  readout рисует библиотека. Здесь панель — целиком наша (порт `controls.ts`):
  слайдер + живое значение + единица, color-input, textarea, select.
- **Каркас 3 колонок + выделение** (в `App.tsx`). У Puck лейаут, undo/redo,
  outline идут из коробки; здесь — grid руками, `SettingsColumn` сам находит
  выделенный узел (`state.events.selected` — это `Set`, берём `[0]`) и рендерит
  его `related.settings`.
- **Сериализация дерево↔документ** (`documentToCraft`/`craftToDocument`). Craft
  хранит дерево **плоской мапой по id** с canvas-узлом `ROOT` и порядком в
  `ROOT.nodes`; собираем/разбираем её вручную. У Puck `Data.content` — уже
  плоский упорядоченный список, изоморфный нашему `SectionNode[]`.

### Что было из коробки у Craft.js (честно в плюс)

- **DnD-механика и состояние-дерево** — `connect`/`drag`/`create` работают сразу,
  reorder и add не пришлось программировать.
- **`related.settings`** — аккуратный способ привязать панель к типу узла: Craft
  сам рендерит её в контексте выделенного узла, `useNode` отдаёт `props`+`setProp`.
- **id чище, чем у Puck**: id узла Craft = наш id секции напрямую; не нужно
  прятать `id` внутрь `props`, как в Puck (`puck-adapter` это делает).

### Замеченные грабли

1. **Анти-drift потребовал разреза компонента.** Craft-обёртка блока использует
   `useNode`, поэтому её нельзя отрендерить через `renderToStaticMarkup` вне
   `<Editor>`. Пришлось вынести **чистый** `BlockHtml` (без хуков) отдельно от
   Craft-обёртки. У Puck render-компонент уже был чистым.
2. **React 19 трение.** Craft 0.2 внутри `connectors.create` читает `element.ref`
   — в React 19 это deprecated, в консоли висит ошибка (нефатальная, превью
   работает). У Puck 0.20 такого шума нет. Риск до-1.0 API — реальный.
3. **Документация vs реальность.** В части примеров проп зовётся `resolvers`, в
   актуальном типе `<Editor>` — `resolver` (единственное число). Сверять по типам.
4. **`Frame data` мемоизируется** — после первого рендера менять начальные узлы
   нужно через `actions.deserialize`, а не пропом (учтено: документ ведём в `ref`,
   синхронизируем через `onNodesChange`).

## Вывод

Гипотеза ADR-0002 подтверждена **и на Craft.js**: редактор успешно оборачивает
наш агностичный строковый render, экспорт остаётся строкой HTML без React,
анти-drift держится. Совместимость — не дифференциатор: проходят оба.

Дифференциатор — **объём и эргономика обвязки**. Craft.js дал DnD-механику, но
палитру, панель и каркас пришлось писать самим — **≈1.9× кода редактора** против
Puck на идентичной функциональности. Это эмпирически подтверждает выбор ADR-0004
(Puck) и оценку «Craft.js = только механика DnD, остальное руками». Резерв за
Craft.js из ADR остаётся в силе: его стоит достать, если упрёмся в ограничения
модели Puck (сильно кастомный холст, глубокая вложенность) — там ручной каркас
окупается контролем.

## Замечания (для Фазы 1) — общие с Puck-спайком

- Конверт в проде — полноэкранный `position: fixed` оверлей; в холсте редактора
  он нейтрализуется локальным CSS (`App.tsx`, `.craft-block[data-block]`). В Фазе 1
  нужен honest «режим холста» для full-bleed секций (на скриншотах конверт без
  full-bleed-фона — именно поэтому).
- `img/seal.png` берётся из реального `public/` (через `publicDir` в
  `vite.config.ts`); вне dev-сервера путь относительный.
- Тип с `/` («intro/envelope») экранируется в ключ resolver'а (`intro--envelope`)
  и возвращается обратно при маппинге.
