# ADR-0006. Потребление дизайн-системы хрома: синк вместо прямого импорта

- **Статус:** принято
- **Дата:** 2026-08-03
- **Контекст задачи:** STUDIO-044 (экспорт ДС), STUDIO-046 (канал), STUDIO-051
  (ограждение); цикл «Новая дизайн-система Studio».

## Контекст

[STUDIO-044](../../../gd-brain/tasks/studio/STUDIO-044/index.md) положил в
репозиторий побайтовый экспорт дизайн-системы хрома из Claude Designer:
`docs/design/styles.css` (слой компонентов `ch-*`),
`docs/design/styles/chrome-tokens.css` (единственное место со значениями
`--chrome-*`), локальный шрифт в `docs/design/assets/fonts/`, витрины и шаблоны
окон.

Продукту эти стили нужно **подключать**, а не только показывать. При этом:

- `docs/design/styles.css` тянет два `@import` (`chrome-fonts.css`,
  `chrome-tokens.css`), а шрифт грузится через `@font-face` с относительным
  путём `../assets/fonts/*.woff2`. Нынешний приём редактора
  (`import chromeCss from './chrome.css?raw'` + `<style>{chromeCss}</style>`)
  на такую таблицу не переносится: внутри инлайн-`<style>` относительные пути
  разрешаются от адреса страницы и ломаются.
- В `styles.css` нет ни одного глобального селектора — всё под `.ch-*`, поэтому
  подключение на уровне страницы безопасно и с контентом холста не сталкивается.
- `public/fonts/golos/` не используется нигде: ни в `render-core/styles/fonts.css`,
  ни в токенах темы, ни в `index.html`. Шрифт лендинга — Source Serif / Florisel /
  Felidae, это другой контур.

Рассматривались три способа потребления: прямой импорт из `docs/`, синк копии в
`src/`, переезд всей ДС внутрь `src/`.

## Решение

**Синк.** Скрипт `ds:sync` копирует из `docs/design/` в `src/editor/ds/`
**явный список файлов** — `DS_FILES` в `scripts/ds-files.mts`:

- `styles.css`,
- `styles/chrome-fonts.css`, `styles/chrome-tokens.css`,
- `assets/fonts/GolosText-{Regular,Medium,SemiBold}.woff2`,
- `assets/fonts/OFL.txt`.

Перечень, а не глоб: `styles/*.css` подтянул бы `styles/docs.css` — таблицу
витрин, продукту не нужную. Плата за явный список — его надо дописывать руками,
когда экспорт приносит новый файл (например, четвёртое начертание). Забытый
файл, на который есть ссылка внутри таблицы (`@import`, `url()` в `@font-face`),
роняет `npm run build`: Vite не разрешит путь. Молча потеряться может только
файл, на который никто не ссылается, — то есть продукту и не нужный.

`DS_FILES` — единственный источник правды о составе: и `ds:sync`, и `ds:check`
читают его, разойтись друг с другом они не могут.

Витрины, шаблоны, `support.js`, `_ds_bundle.js` и `_ds_manifest.json` **не
копируются** — продукт их не подключает.

Копия **коммитится в git**: `src/` остаётся самодостаточным, свежий клон
собирается без дополнительных шагов. Правда одностороння: правится только
исходник в `docs/design/`; правка синкнутой копии — такая же ошибка, как правка
`src/tokens/dist/`.

Расхождение копии с исходником ловит `ds:check` — **побайтовая** сверка
(sha256 по каждому файлу из `DS_FILES`), подключённая в `npm run verify`. Это тот
же критерий, что уже работает для экспорта из Designer: «повторный прогон даёт
пустой diff». Сверх хешей `ds:check` требует, чтобы в `src/editor/ds/` лежали
**ровно** файлы из `DS_FILES`: лишний файл в копии — тоже ошибка, иначе список
можно было бы обойти ручной подкладкой.

Вместе с переездом:

- `src/editor/chrome.css` удаляется целиком (а не переписывается на токены);
- `public/fonts/golos/` удаляется как мёртвый груз;
- в `src/editor/` не остаётся ни одного собственного `.css` — только синкнутая
  `ds/`. Это машинно проверяемый инвариант (STUDIO-051).

## Почему не прямой импорт из `docs/`

Прямой `import '../../docs/design/styles.css'` дешевле (ноль копий, ноль синка,
Vite сам инлайнит `@import` и переписывает пути шрифтов), но делает `docs/`
участником сборки: сломанный экспорт роняет `npm run build`, а не только
витрину. Выбор в пользу синка сознательно платит дублированием байтов
(~20 КБ CSS + три `woff2`) за то, что зависимость `src/ → docs/` остаётся
только у скрипта, а не у бандла.

## Почему не переезд ДС внутрь `src/`

Переезд (Designer пишет прямо в `src/chrome-ds/`) убирает дублирование вовсе,
но затаскивает в `src/` HTML-витрины и `support.js` (69 КБ), где живут lint и
сборка. Вариант остаётся запасным на случай, если сверка копии окажется дороже,
чем кажется.

## Последствия

- Появляются цели `ds:sync` и `ds:check`; `ds:check` входит в `verify`.
- Обновление ДС — ритуал из двух шагов: переэкспорт из Designer в `docs/design/`,
  затем `ds:sync`. Забыть второй шаг нельзя — `verify` станет красным.
- Если переэкспорт меняет **состав** ДС (новый файл стилей, новое начертание),
  ритуал удлиняется на шаг: дописать `DS_FILES` в `scripts/ds-files.mts`.
- В редакторе сосуществуют два способа подключения стилей, и это намеренно: хром
  приезжает таблицей из ДС, а CSS холста и экспорта (`base.css`, `fonts.css`,
  модули секций) остаётся `?raw`-строками, потому что уезжает в статический
  артефакт.
- Превью-статус Claude Design (research preview) циклу не мешает: ДС уже лежит в
  git, и `ds:sync` копирует из репозитория, а не из сети. Подробнее — решение D9
  в gd-brain.
