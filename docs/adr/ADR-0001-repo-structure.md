# ADR-0001. Структура репозитория: один пакет vs монорепо

- **Статус:** принято
- **Дата:** 2026-06-20
- **Контекст задачи:** STUDIO-003 (каркас репозитория), Фаза 0 роадмапа.

## Контекст

Студии нужна структура под архитектуру роадмапа с явной границей между будущими
частями:

- `render-core` — агностичный к React render и реестр блоков (ванильный TS);
- `sections` — модули секций;
- `tokens` — токены темы;
- `editor` — React-оболочка редактора (появится на Фазе 1, STUDIO-008).

Ключевое требование — **прод-выход не должен тащить React**: render остаётся
лёгким и независимым. Возникает развилка: оформить это как **один пакет** (папки
внутри одного `package.json`) или сразу как **монорепо** (отдельные пакеты в
workspaces).

## Решение

На Фазе 0 используем **один пакет** (single-package repo). Граница «агностичный
render vs React-оболочка» держится **дисциплиной структуры**: код в
`src/render-core/` и `src/sections/` не импортирует React; React живёт только в
будущем `src/editor/` и точке входа `src/main.tsx`.

## Обоснование

- **Нет внешних потребителей пакетов.** Это личный/агентский инструмент, не
  публикуемые библиотеки. Разделение на npm-пакеты сейчас не даёт ценности.
- **Меньше оснастки.** Монорепо тянет workspaces, сборку пакетов, версионирование
  и таск-раннеры (turbo/nx) — преждевременная сложность для пустого каркаса.
- **Граница не требует пакетов.** Агностичность render обеспечивается контрактом
  и правилом импортов (при необходимости — линт-границы), а не физическим
  разнесением по пакетам.
- **Обратимость.** Переход «один пакет → монорепо» дешёвый: папки `render-core` /
  `tokens` уже выделены и при необходимости станут отдельными пакетами.

## Последствия

- Один `package.json`, один набор зависимостей, единые скрипты dev/build/preview.
- Агностичность render — соглашение, за которым следим ревью/линтом (не гарантия
  системы сборки).
- К монорепо вернёмся, если `render-core` или `tokens` понадобится публиковать
  или переиспользовать в отдельном проекте (потенциальный ADR-будущего).
