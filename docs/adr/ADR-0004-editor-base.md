# ADR-0004. Основа визуального редактора (Puck / Craft.js / @dnd-kit)

- **Статус:** принято предварительно — Puck как рабочий дефолт; **финальный выбор
  движка отложен до показательного прототипа** (см. аддендум «Требования к
  редактору и отложенное решение»).
- **Дата:** 2026-06-21
- **Контекст задачи:** STUDIO-008 (основа редактора), мост между Фазой 0 и Фазой 1 роадмапа.

## Контекст

Фазе 1 нужен drag-and-drop (DnD) редактор лендингов. Главное ограничение задаёт ADR-0002: наш
**render — чистая функция `(props, ctx) → строка HTML`**, агностичная к React;
React в прод-вывод **не попадает**. Puck/Craft.js же редактируют дерево **React-
компонентов**. Значит, редактор не может рендерить блоки «по-своему» (это создало
бы второй путь рендера и классический drift WYSIWYG-билдеров) — он должен
**оборачивать** наш строковый render.

Отсюда форма решения («гибрид» из роадмапа): React — оболочка редактора и тонкая
обёртка блока (`mod.render` → `dangerouslySetInnerHTML`), а модель данных
редактора маппится в/из нашего `StudioDocument` (ADR-0004 не меняет ни контракт
render, ни документ-модель STUDIO-004).

## Кандидаты

| Кандидат            | Что даёт                                                                                                                                     | Минус                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| **Puck** (MIT)      | Готовый редактор: палитра, DnD, панель полей из конфига; модель = упорядоченный список компонентов с props — близко к нашему `SectionNode[]` | Свой формат `Data` → нужен адаптер; API до 1.0   |
| **Craft.js** (MIT)  | Механика DnD + дерево состояния; UI редактора пишешь сам                                                                                     | Вся обвязка (палитра, панель, тулбар) — руками   |
| **@dnd-kit** (своё) | Максимальный контроль                                                                                                                        | Наибольший объём работы; переизобретаем редактор |

## Критерии и итог спайка

Спайк (`spikes/editor/`) собрал мини-редактор на **Puck** поверх реальных модулей
`intro/envelope`, `hero`, `closing` и нашего `renderDocument`.

| #   | Критерий                                                                  | Вердикт по Puck                                                                                     |
| --- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 1   | Совпадение модели с `StudioDocument`/`SectionNode[]` (порядок, props, id) | ✓ `documentToPuck`/`puckToDocument` — тонкий маппинг; round-trip (туда-обратно) без потерь          |
| 2   | Панель свойств из нашей `ParamSchema` (range/color/text/select)           | ✓ `fieldsFromSchema`: range→number, text→textarea, select→select, color→custom `<input type=color>` |
| 3   | Инлайн-превью живым render                                                | ✓ `BlockPreview` зовёт `mod.render` → `dangerouslySetInnerHTML`; рисуется в холсте                  |
| 4   | DnD: добавить/переставить/удалить + дробный `order`                       | ✓ палитра/Outline Puck; `order` пересчитывается через fractional-indexing                           |
| 5   | Вес бандла **редактора** (на вывод не влияет)                             | ✓ Puck только в спайке; прод-`vite build` остаётся без него (бандл не вырос)                        |
| 6   | Зрелость API, лицензия, кастомные поля                                    | ✓ MIT, v0.20, React 18/19, тип поля `custom` для нестандартных контролов                            |
| 7   | Объём адаптера «строковый render ↔ React-обёртка»                         | ✓ один файл `puck-adapter.tsx` (~150 строк), без правок `render-core`                               |

Headless-проверка `verify.mts` дополнительно подтверждает **анти-drift**:
`renderToStaticMarkup(BlockPreview)` содержит **ровно** строку `mod.render` — то
есть оболочка не порождает второй разметки, а экспорт через `renderDocument`
остаётся строкой HTML без следов React.

## Решение

База редактора Фазы 1 — **Puck (MIT)**.

Архитектура интеграции (зафиксирована спайком):

- На каждый тип блока — Puck-компонент, чей `render` = React-обёртка
  `BlockPreview`, вызывающая агностичный `mod.render(props, ctx)`.
- Панель свойств генерируется из `ParamSchema` модуля (`fieldsFromSchema`).
- Состояние редактора (`Puck.Data`) маппится в/из `StudioDocument`
  (`documentToPuck` / `puckToDocument`); порядок секций — наш дробный `order`.
- **Экспорт не меняется:** идёт через `renderDocument` (Node, без React) —
  единый путь рендера для превью и прода.

## Обоснование

- **Минимальный адаптер.** Модель Puck (упорядоченный список компонентов с props)
  изоморфна `SectionNode[]` — мост умещается в один файл, ядро не трогается.
- **Готово из коробки.** Палитра, DnD, панель полей, undo/redo, viewport-режимы —
  из коробки; не переизобретаем то, что в `@dnd-kit`-варианте писалось бы руками.
- **Декларативная панель** хорошо ложится на schema-driven подход (ADR-0003), а
  тип поля `custom` закрывает наши нестандартные контролы (цвет, в будущем — карта).
- **Совместимость с ADR-0002 доказана спайком**, а не принята на веру.

## Последствия

- В Фазе 1 появляется `src/editor/` (React-оболочка) — `BlockPreview`,
  `fieldsFromSchema`, `documentToPuck`/`puckToDocument` переносятся из спайка в
  продакшн-форме; `render-core`/`sections` остаются агностичными (ADR-0001/0002).
- `ParamSchema` → поля Puck — переходный слой. Если на Фазе 1 победит **JSON
  Schema + UI Schema** (см. ADR-0003 «Пересмотр»), адаптер полей просто меняет
  источник — модель блока и render не затрагиваются.
- Зависимость от до-1.0 API Puck — риск ломких обновлений; фиксация (pin) версии, обёртка
  изолирует наш код от его API.
- Full-bleed секции (конверт — `position: fixed`) требуют честного «режима холста»
  в редакторе — отмечено в спайке как задача Фазы 1.

## Отклонено

- **Craft.js** — даёт только механику DnD; палитру, панель и тулбар пишем сами.
  Резерв: вернёмся, если понадобится сильно кастомный холст или глубокая
  вложенность, которых не покрывает модель Puck.
- **Своё на @dnd-kit** — максимум контроля ценой переизобретения редактора;
  не оправдано, пока Puck закрывает требования (вернуться лишь если упрёмся в его
  ограничения).
- **Render как React-компоненты на блок** — отклонено ещё в ADR-0002 (React в
  выводе, второй путь правок, drift). Puck используется поверх строкового render,
  а не вместо него.

## Дополнение (addendum): эмпирическая сверка с Craft.js (спайк `spikes/editor-craft/`)

После принятия решения собран **зеркальный** спайк на Craft.js
([`spikes/editor-craft/`](../../spikes/editor-craft/)) поверх тех же модулей и
того же `renderDocument` — чтобы сравнить кандидатов по факту сборки, а не по
оценке. Решение ниже **не меняется** — аддендум лишь подкрепляет его цифрами.

Совместимость с ADR-0002 подтвердилась **и на Craft.js**: редактор оборачивает
строковый render, экспорт остаётся строкой HTML без React, анти-drift держится
(`verify.mts` [5]). То есть совместимость — **не дифференциатор**, её проходят оба.

Дифференциатор — **объём и эргономика обвязки** на идентичной функциональности:

| Часть редактора                     |                     Puck |                 Craft.js |
| ----------------------------------- | -----------------------: | -----------------------: |
| Адаптер модель↔редактор             |                      175 |                      230 |
| Панель свойств из `ParamSchema`     | ~22 (`fieldsFromSchema`) | 109 (`SchemaFields.tsx`) |
| Палитра / Toolbox                   |           0 (из коробки) |                       47 |
| Каркас + выделение + экспорт        |                      142 |                      223 |
| **Код редактора (без verify/main)** |                 **≈317** |         **≈609 (≈1.9×)** |

Прирост — ровно те части, что Puck даёт из коробки: палитра, декларативная
панель полей, каркас с DnD и выделением. Главная грабля Craft.js: анти-drift
потребовал разрезать блок-компонент (Craft-обёртка зовёт `useNode` и не
рендерится через `renderToStaticMarkup` вне `<Editor>`), плюс трение Craft 0.2 с
React 19 (`element.ref`). Вывод сверки совпал с решением: **Puck**; резерв за
Craft.js остаётся для сильно кастомного холста/глубокой вложенности, где ручной
каркас окупается контролем. Подробный разбор — в README спайка.

## Дополнение (addendum): открытые вопросы — кастомные модификаторы и inline-редактирование

Подняты **после** принятия решения. Решение (Puck) **не меняется** — это
зафиксированные риски/критерии для пересмотра на Фазе 1. Главный вывод: оба
вопроса упираются не столько в движок, сколько в **гранулярность нашего render
(ADR-0002)**, поэтому записаны здесь как открытые.

### 1. Кастомные модификаторы (контролы панели)

Исходная посылка «в Puck нельзя сделать модификаторы как хочется» — **неверна**.
Puck это умеет тремя слоями:

- `custom` field type — произвольный React-контрол на поле (в спайке так сделан
  color-input);
- `overrides.fieldTypes` — заменить или **добавить новый тип поля** глобально
  (например, геометрический редактор клапанов конверта как тип `flapEditor`);
- плагины (`fieldTypes` + `fieldTransforms`) — в т.ч. оверлеи (overlays) поверх холста.

Разница с Craft.js — **степень владения панелью**, а не «можно/нельзя»:

|                                   | Puck                         | Craft.js                                                   |
| --------------------------------- | ---------------------------- | ---------------------------------------------------------- |
| Что твоё                          | контрол поля (и тип поля)    | **вся панель целиком** (`related.settings` — чистый холст) |
| Чьи компоновка/оркестровка панели | Puck (сайдбар, строки полей) | твои (любая раскладка, инструменты у холста)               |

Под видение «модификаторы и их раскладка — полностью мои» Craft.js свободнее.
Это аргумент к **пересмотру**, если bespoke-панель станет ключевой ценностью; но
он не отменяет готовые возможности Puck для типового случая.

### 2. Inline-редактирование текста

Под inline здесь понимается: текст правится **и в боковом поле справа, и прямо в
центральном холсте**, причём в холсте — **только текстовая каретка, без тулбаров и
модификаторов**.

Это **не ограничение Puck**: inline умеют оба движка (Puck — `richtext` /
`contentEditable` / `registerOverlayPortal`; Craft.js — `contentEditable` +
`setProp` на узле). Настоящая зависимость — **гранулярность render (ADR-0002)**.

**Гранулярность** = уровень адресуемой единицы правки. Сейчас блок рендерится
одной непрозрачной строкой HTML (`dangerouslySetInnerHTML`), и редактор видит один
узел с props — связь «текст в DOM ↔ какой prop» потеряна. Поставить каретку в
`<h1>` hero и вернуть правку именно в `names` нельзя: на input приходит вся строка,
надёжно сопоставить её с конкретным prop не выйдет. Чтобы inline заработал, нужна
мелкая гранулярность — одним из путей (это выбор по ADR-0002, не по движку):

- **(а) Дробление на под-узлы:** `hero` → контейнер с под-узлами
  `eyebrow`/`names`/`date`; каждый рендерится сам и редактируется кареткой. Меняет
  документ-модель; естественно для дерева Craft.js (в Puck — через DropZones/slots).
- **(б) Render-с-якорями (легче под «только каретка»):** строковый render остаётся,
  но помечает редактируемые места — `<h1 ... data-prop="names" contenteditable>`;
  редактор слушает `input` на элементе с `data-prop` и пишет в нужный prop. Модель
  не дробим, добавляется тонкий edit-time слой; ADR-0002 (строковый render)
  сохраняется. Минус — это второй, edit-time путь, который надо держать без drift.

Влияние на выбор движка: путь (а) дружелюбнее к дереву Craft.js, путь (б) — к
модели Puck + `registerOverlayPortal`. Оба реализуемы на обоих. **К пересмотру
ADR-0004 вернуться, когда будет решена гранулярность render (ADR-0002).**

> **Обновление (2026-06-21):** гранулярность render решена — путь **(б), якоря
> `data-prop` + `contenteditable`** (см. [ADR-0002](ADR-0002-render-contract.md),
> дополнение «Гранулярность render для inline-правки»). В пути (б) inline
> **движок-нейтрален** (редактируемый элемент — чужой DOM внутри HTML-блоба, на
> обоих движках write-back делается своим listener'ом), поэтому inline-каретка
> **перестаёт быть дифференциатором** Puck↔Craft. Решающей для прототипа остаётся
> ось 1 — **владение UX редактора**. Выбор движка по-прежнему отложен.
>
> **Обновление (2026-06-21, STUDIO-015 — inline-каретка реализована на Puck.)**
> Edit-time слой собран в `src/editor/inline-edit.tsx` (`overrides.puck` +
> `iframe.enabled = false`). Puck-специфика, выявленная при реализации: Puck
> оборачивает блок в DnD-контейнер (`[data-puck-dnd]`) с `pointer-events: none`
> на содержимом, поэтому для каретки на якоре **обязательны** `pointer-events:
auto` + `registerOverlayPortal` (детали и причина — в
> [ADR-0002](ADR-0002-render-contract.md), обновление STUDIO-015). На выбор движка
> это не влияет (ось 1 «владение UX» остаётся решающей), но фиксирует, что
> `registerOverlayPortal` для Puck-пути inline — не опция, а необходимость.

## Дополнение (addendum): требования к редактору и отложенное решение

После доп. вопросов зафиксированы требования к будущему редактору и сверены с
актуальной докой Puck. **Главный вывод: на возможностях Craft.js не обгоняет Puck**
— видео, анимация и кастомизация UI у Puck есть; где возникает трение, виновник —
наш строковый render (ADR-0002), а не движок. Поэтому **финальный выбор движка
отложен до показательного прототипа**; решение Puck действует как рабочий дефолт.
Откладывание почти ничего не стоит, потому что миграция дёшева по архитектуре (by design) (см. ниже).

### Сверка требований (по докам)

| #   | Требование                                                                     | Вердикт                                                                                                                                                                                                                                                                                                                                                  | Дифференциатор Puck↔Craft?                     |
| --- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 1   | Редактор **компонентов** (визуальное авторство блоков)                         | Ни Puck, ни Craft этим не являются — оба лишь _расставляют/настраивают_ блоки, написанные кодом (`BlockModule` = render + `ParamSchema`). Это отдельный слой поверх, ортогональный движку. Компоненты = ручная работа.                                                                                                                                   | Нет (слабый крен к Craft на низком уровне)     |
| 2   | **Кастомизация UI** редактора: убрать/добавить/переставить панели, сменить вид | Puck закрывает ~90%: `overrides` (header, fields, outline, actionBar, список, типы полей) + **композиция** (`<Puck.Preview/>`/`<Puck.Components/>`/`<Puck.Fields/>`/`<Puck.Outline/>` в своей вёрстке). Предел — рекомпоновка регионов Puck. Craft = чистый лист, 100% свобода.                                                                          | Частичный (Craft свободнее на «весь UX — мой») |
| 3   | **Цена переезда** Puck→Craft при упоре в стену                                 | **Низкая, по архитектуре (by design)**: ядро (`render-core`/`sections`/`document`/`schema`) агностично; движок — только тонкий адаптер. Craft-адаптер+UI **уже собран** (`spikes/editor-craft/`, ~600 строк). Переезд = переписать `src/editor/`, ядро не трогается.                                                                                     | Снимает риск выбора                            |
| 4   | **Проигрыватель анимации** компонентов                                         | Puck не мешает: превью — живой React. В нашем строковом render CSS-анимации работают в холсте у обоих (конверт уже анимируется). «Плеер» (play/pause/scrub) и JS-анимация по вставленному HTML — кастом одинаково у обоих.                                                                                                                               | Нет                                            |
| 5   | **Видео-компоненты** и воспроизведение в редакторе                             | Тривиально у обоих: блок отдаёт `<video controls src>`, играет в холсте (живой DOM). Puck это не ограничивает.                                                                                                                                                                                                                                           | Нет                                            |
| 6   | Прочие ограничения Puck                                                        | до-1.0 API (ломкие обновления); модель React-дерева (slots/inline) vs наш строковый render → глубокая вложенность и inline упираются в гранулярность ADR-0002; full-bleed/`fixed` секции требуют честного «режима холста»; UX с навязанными решениями (opinionated) (тотальная переделка = борьба); привязка к формату `Data` (lock-in) снята адаптером. | Частичный                                      |

### Что должен показать прототип (решающие критерии)

Видео и анимация **подтверждены как НЕ дифференциаторы** — их не проверяем.
Прототип (на обоих движках, на нашем ядре) должен дать ответ ровно по двум осям:

1. **Владение UX редактора.** Собрать целевую раскладку (нужные панели убраны/
   добавлены/переставлены, свой вид): на Puck — через `overrides` + композицию; на
   Craft — с нуля. Сравнить, упираемся ли в рамки Puck на желаемом UX.
2. **Inline-каретка в холсте** (правка текста прямо в центре, без модификаторов)
   под выбранную **гранулярность render** (ADR-0002): путь (а) дробление на
   под-узлы или (б) render-с-якорями (`data-prop` + `contenteditable`). Это решение
   по ADR-0002; движок вторичен (дерево Craft дружелюбнее к (а), `registerOverlayPortal`
   Puck — к (б)).

### Почему откладывание безопасно

Архитектура ADR-0001/0002 делает движок **сменным**: источник правды —
`StudioDocument`, render агностичен, движок изолирован адаптером. Дешевизна держится
**только при строгой границе**: никаких типов Puck в `render-core`/`sections`. Пока
это соблюдается, выбор Puck обратим, а `spikes/editor-craft/` остаётся готовым
шаблоном миграции. **К пересмотру вернуться по итогам прототипа и решения по
гранулярности render (ADR-0002).**
