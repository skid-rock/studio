# ADR-0002. Контракт агностичного render

- **Статус:** принято
- **Дата:** 2026-06-20
- **Контекст задачи:** STUDIO-005 (реестр блоков и render-контракт), Фаза 0 роадмапа.

## Контекст

Студии нужен **общий render** для превью в редакторе (React, Фаза 1) и для
статического экспорта (Node), без drift между превью и продом и без тяжёлого
рантайма в выходном артефакте.

Паттерн уже проверен в `wed`: `renderEnvelope` рисует конверт и в песочнице, и на
лендинге одним кодом. При обобщении на дерево секций это правило нужно зафиксировать
явно.

## Решение

Render блока — **чистая функция** `(props, ctx) → HTML-строка`, агностичная к
фреймворку, **без обращения** к глобальному `document` / `window` / DOM API
(должна работать и в Node).

Контракт модуля в реестре:

```
type → { schema, defaults, render, css?, js? }
```

`renderDocument(doc, { registry })` обходит секции документа в порядке `order`,
вызывает `render` каждого известного типа, собирает `html` и дедуплицированный
`css`. Один и тот же код используется:

- в превью редактора (HTML вставляется в контейнер, напр. `dangerouslySetInnerHTML`);
- в статическом экспорте (Node, без React).

Сборку полной страницы (`doctype`, `<style>` темы, `<style>` блоков, обёртка)
делает отдельный слой (STUDIO-009); `renderDocument` отдаёт только содержимое
`<body>` и CSS модулей.

## Обоснование

- **Анти-drift:** второй путь рендера (React-компоненты «только для превью»)
  неизбежно расходится с продом — классическая болезнь WYSIWYG-билдеров.
- **Анти-bloat:** React не попадает в прод-выход; артефакт — лёгкий HTML/CSS.
- **Eject / no lock-in:** документ + render дают самостоятельный статический
  сайт без рантайма студии.

## Последствия

- React (если будет в редакторе) **только оборачивает** результат render, но не
  участвует в прод-выводе.
- Код в `src/render-core/` и `src/sections/` **не импортирует React** (соглашение
    - ревью/линт).
- Неизвестный `type` в документе **не роняет** render — HTML-комментарий-заглушка.
- CSS модулей дедуплицируется по `type` (один блок CSS на тип секции).

## Отклонено

- **Render как React-компоненты на блок** — тащит React в вывод, усложняет Node-экспорт,
  создаёт второй путь правок.
- **Отдельный «preview renderer»** — гарантированный drift; см. extra-insights §5.

## Дополнение (addendum): гранулярность render для inline-правки — решение (б), якоря

Поднято на мосту Фаза 0 → Фаза 1 (см. [ADR-0004](ADR-0004-editor-base.md)).
Inline-правка текста (M4 роадмапа) упирается не в движок редактора, а в
**гранулярность этого контракта**: блок отдаёт одну непрозрачную строку HTML, и
редактор видит один узел с плоскими props — связь «текст в DOM ↔ какой prop»
потеряна. Решение по гранулярности — здесь, в ADR-0002; ADR-0004 (движок) от него
зависит, не наоборот.

### Решение

Inline-правка реализуется путём **(б) — render с якорями**, не дроблением на
под-узлы:

- Строковый render сохраняется как есть — **основное решение ADR-0002 не меняется**
  (один путь рендера для превью и прода).
- Render помечает редактируемые места **инертными атрибутами**:
  `<h1 ... data-prop="names" contenteditable>`. Атрибуты одинаковы в превью и в
  экспорте; `contenteditable` — edit-time, слой сборки страницы (STUDIO-009)
  снимает его в прод-выводе.
- Правится **весь текст элемента-якоря**: значение prop = текстовое содержимое его
  элемента.
- **Дисциплина якорей нестрогая.** Типовой случай — один prop = один leaf-элемент
  (как `hero`: `names`/`eyebrow`/`date`). Смешанные случаи (литерал + значение в
  одном элементе, напр. `closing`: `P.S. ${ps}`) — **частный случай**, решаемый
  **преднастроенными компонентами** (секция/блок, где «P.S.» уже зашит в разметку,
  а правится только переменная часть), а не дроблением модели.
- **Rich-text пока не вводим.** Дизайн приходит из Figma с готовыми
  шрифтами/форматированием; вероятно блоки будут с пресетами и плоским текстом.
  Потребность в rich-text проверяется только реальной эксплуатацией (возможно — не
  первой) — см. триггеры пересмотра.

### Контракт edit-time слоя (как держим анти-drift)

- **Якоря — часть строки render**, не второй рендерер. Тот же `mod.render` даёт и
  превью, и экспорт; якорь — inert-атрибут в этой строке.
- **Read:** редактор слушает `input` на элементе с `data-prop` и берёт **raw**-текст
  каретки (`textContent`), а не уже экранированное значение.
- **Un-escape:** значения экранируются на рендере (`esc()` в модулях секций);
  write-back пишет в prop сырой текст — без повторного `esc`.
- **Write:** редактор пишет значение в `props[dataProp]` соответствующего узла
  (через API движка — см. ниже); источник правды остаётся `StudioDocument`,
  ре-рендер точечный (только изменённый блок).
- **Граница ADR-0001:** `render-core`/`sections` про редактор не знают; якорь —
  это лишь атрибут в разметке секции, edit-time-логика живёт в `src/editor/`.

### Движок-нейтральность (Puck и Craft.js)

В пути (б) редактируемый элемент живёт внутри непрозрачного HTML-блоба
(`dangerouslySetInnerHTML`), и **движок не считает его своим узлом** — знает только
узел-обёртку секции. Поэтому write-back — собственный listener на `[data-prop]` на
обоих движках:

- **Puck:** listener (у нас — `focusout`, коммит на blur) → `dispatch(setData)`,
  пишущий в props узла. **`registerOverlayPortal` + `pointer-events: auto` на якоре
  — обязательны, не опция** (см. ниже, обновление STUDIO-015).
- **Craft.js:** listener `input` → `setProp(nodeId, …)`.

Объём одинаков. Нативный per-node `contentEditable` Craft включается **только в
пути (а)**. Значит (б) **снимает движок как дифференциатор для inline** —
согласуется с отложенным выбором движка (ADR-0004).

> **Обновление (2026-06-21, STUDIO-015 — реализация пути (б) на Puck).**
> При реализации inline-каретки выяснилось, что для Puck связка
> `registerOverlayPortal` + `pointer-events: auto` на якоре **обязательна**
> (выше в тексте `registerOverlayPortal` значился как «опц.» — это уточнение
> отменяет «опционально»). Причина: Puck оборачивает каждый блок в DnD-контейнер
> (`[data-puck-dnd]`) и выставляет на содержимом блока **`pointer-events: none`**,
> перехватывая клики на уровне обёртки (выделение/drag узла). Без вмешательства
> клик по тексту не доходит до `[data-prop]`, каретка не появляется — хотя
> write-back на blur при программном фокусе уже работает. Что делает edit-time
> слой на каждом якоре:
>
> 1. `contenteditable = 'plaintext-only'` (включение правки);
> 2. `style.pointerEvents = 'auto'` (пробить `pointer-events: none` Puck);
> 3. `registerOverlayPortal(el)` — официальный API Puck: помечает элемент как
>    интерактивный «портал» поверх холста, гасит перехват кликов/drag DnD-обёрткой
>    при фокусе (и снимает пометку в cleanup).
>
> Это **Puck-специфика** (атрибут `data-puck-dnd` и его `pointer-events: none`),
> а не часть агностичного контракта — поэтому живёт целиком в `src/editor/`
> (`inline-edit.tsx`), `render-core`/`sections` не затронуты (граница ADR-0001).
> Для Craft.js (путь (б)) аналога не потребуется — там перехват кликов устроен
> иначе; конкретику зафиксировать, если/когда соберём inline на Craft.

### Плюсы / минусы (б) — выбранный путь

**Плюсы:**

- Сохраняет ADR-0002 в полном объёме: один строковый render, без второго пути.
- Дёшев: расширяет уже работающий механизм вставки (`dangerouslySetInnerHTML` +
  `data-block` из спайка) на один атрибут.
- Не требует неимплементированной инфраструктуры `children` (в модели объявлена,
  но операции и render — плоские).
- Движок-нейтрален → не привязывает inline к Puck, не даёт Craft повода «обогнать».
- Документ-модель остаётся плоской → меньше миграций («документы переживают код»).

**Минусы:**

- Появляется тонкий **edit-time путь** (listener + un-escape), который надо держать
  без drift с render.
- Гранулярность ограничена **уровнем элемента-якоря**: правка под-частей текста и
  rich-text «из коробки» недоступны.
- Смешанные литерал+значение кейсы требуют аккуратной разметки (значение —
  единственное содержимое своего элемента) либо преднастроенных компонентов.
- Нет структурной правки внутри секции (переставить/добавить под-блоки) — секция
  остаётся атомом.

### Плюсы / минусы (а) — резервный путь (дробление на под-узлы)

**Плюсы:**

- Inline «бесплатно»: каждый текст — настоящий узел, правится нативно (особенно
  дерево Craft.js).
- Структурная правка внутри секции: под-блоки можно добавлять/переставлять/удалять.
- Естественно ложится на rich-text и глубокую вложенность.
- Гранулярность явная, в самой модели — без edit-time-«магии» якорей.

**Минусы:**

- Меняет документ-модель: `children` из «объявлено» в «реализовано везде».
- Множит число узлов; авторинг секции превращается в композицию под-блоков.
- Больше поверхности для миграций схемы (`schemaVersion`).
- Геометрические/full-bleed секции (envelope) болезненно дробить на под-узлы.

### Чек-лист миграции (б) → (а)

Что конкретно надо построить, чтобы переключиться (сейчас этого нет):

1. **Рекурсия в операциях модели**
   ([document.ts](../../src/render-core/document.ts)):
   `addSection`/`moveSection`/`removeSection` сейчас плоские — научить обходу и
   правке `children` (адресация по родителю/пути).
2. **Рекурсивный `renderDocument`** ([render.ts](../../src/render-core/render.ts)):
   обход `children`, склейка HTML под-узлов в слот контейнера.
3. **Контейнерные блоки в реестре**
   ([registry.ts](../../src/render-core/registry.ts),
   [types.ts](../../src/render-core/types.ts)): семантика «блок-контейнер рендерит
   детей в слот», валидация допустимых детей.
4. **Маппинг дерева в движок:** `documentToPuck`/`puckToDocument` (или
   Craft-эквивалент) сейчас маппят плоский `content` — нужен перенос вложенности
   (Puck DropZones/slots или дерево Craft).
5. **Миграция схемы:** `schemaVersion++` и трансформер «плоская секция →
   контейнер + под-узлы» для существующих документов.
6. **Inline через нативный узел:** заменить listener `[data-prop]` на нативный
   `contentEditable` узла (выигрыш Craft материализуется именно здесь).

Миграция **аддитивна и частична**: дробить можно только те секции, где это нужно,
остальные оставить плоскими — якоря (б) и под-узлы (а) сосуществуют. Это и есть
страховка дешёвой смены.

### Триггеры пересмотра (когда брать (а))

- Понадобилась **структурная правка внутри секции** (пользователь переставляет/
  добавляет под-блоки, а не только правит текст).
- Реальная эксплуатация показала потребность в **rich-text как отдельных единицах**
  (форматирование, ссылки внутри абзаца, повторяющиеся под-элементы).
- **Глубокая вложенность**, которую неудобно держать плоскими props.
- Дисциплина якорей системно ломается (много смешанных литерал+значение кейсов,
  преднастроенные компоненты не спасают).

До наступления триггеров — путь (б); ясность по rich-text/структуре ожидается
только из реальной эксплуатации.

## Дополнение (addendum): доставка клиентского JS секции (STUDIO-019)

Некоторым секциям нужен минимальный клиентский скрипт (countdown — тик). Контракт
расширен **аддитивно**, основное решение ADR-0002 не меняется:

- Модуль может отдать статичную строку `js?` (как `css?`) — ОДНУ на тип
  (дедуп в `renderDocument` → `RenderResult.js`). Render по-прежнему чистая строка;
  `js` НЕ исполняется на рендере (агностичность сохранена) — это данные.
- Исполнение — ТОЛЬКО в браузере: `buildPage` кладёт `<script>` перед `</body>`
  (экспорт/прод); в холсте редактора — edit-time бридж `src/editor/section-scripts.tsx`
  (граница ADR-0001 цела: core/sections про редактор не знают).
- Per-instance данные — через data-атрибуты разметки (напр. `data-countdown-target`),
  не через генерацию кода: один скрипт обслуживает N экземпляров.
- **Скрипт обязан быть идемпотентным и самоочищающимся** (таймер на DOM-узле,
  гашение при откреплении) — бридж может прогонять его после каждого ре-рендера.

## Дополнение (addendum): идентичность экземпляра секции (STUDIO-061, ADR-0008)

`RenderContext` несёт не только документ, но и `sectionId` — id узла, который
рендерится сейчас. Расширение **аддитивное**, чистота render не нарушена: контекст
остаётся входными данными, а не каналом побочных эффектов.

- Идентичность экземпляра **не** попадает в `props`: `parseBySchema` отбрасывает
  всё вне схемы, а класть её в схему нельзя — она вылезет в панель свойств как
  редактируемое поле.
- `renderDocument` собирает контекст **на каждый узел** (раньше — один на
  документ); edit-time мост холста кладёт туда `id`, снятый со служебных props.
- Нужна там, где модулю требуется уникальный на странице HTML-id: якорь попапа
  RSVP (`#rsvp-<sectionId>`), иначе два экземпляра секции делят один якорь.
- Разбор решения и отклонённые альтернативы —
  [ADR-0008](ADR-0008-section-instance-identity.md).
